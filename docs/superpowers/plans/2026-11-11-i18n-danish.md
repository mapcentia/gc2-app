# Multi-language support (Danish) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make gc2-web multilingual with Danish as the first translation, chosen from the browser's language preference.

**Architecture:** A small `src/i18n/` module detects the language once at startup from `navigator.languages`, initialises `i18next` with two bundled JSON files (`en.json` is the source of truth, `da.json` the translation) and exposes typed `t` keys. Every feature folder is then converted from hard-coded English to `t(...)` calls, one folder group per task. A guard test scans `.tsx` files for leftover hard-coded text; each task removes its folders from the guard's pending list, so a task is done when the guard passes for its folders.

**Tech Stack:** React 19, TypeScript 5.9, Vite 7, Ant Design 6, `i18next`, `react-i18next`, `vitest` (new, dev only), npm.

**Spec:** `docs/superpowers/specs/2026-11-11-i18n-danish-design.md` — read it before any task. Its decisions 1–8 and the "Danish style" section are binding.

## Global Constraints

- Language: first entry in `navigator.languages` whose primary subtag is `da` or `en` wins; neither present → `en`. No switcher, nothing cached in localStorage/cookies.
- With a non-Danish browser the app must read exactly as it does today: every `en.json` value is the current English string, character for character.
- `src/layout/SideMenu.tsx` labels and group headings are not translated.
- Page titles that match a menu item stay English ("Schemas", "Tile Seeder").
- English in Danish text (never translate): Schema, Table, Column, Index, Constraint, View, Primary key, Sequence, Layer, Class, Style, Label, Tile, Tile Cache, Tile Seeder, Job, Snapshot, Rule, Key/Value, JSON-RPC, Function, OAuth Client, Scheduler, Realtime, Metadata, GraphQL, SQL. Unlisted word: apply the spec's rule; in doubt keep English. Spell `Constraint` correctly.
- Danish for everyday words: bruger, brugernavn, gruppe, rettighed, række, navn, beskrivelse, kommentar, datatype.
- Never use "skema", "indeks", "begrænsning".
- The MapServer property labels in `src/features/map/fieldDefs.tsx` are left untouched.
- Shown as received, no mapping: server error messages, job/run status values, `none`/`read`/`write`, TABLE/VIEW/MAT. VIEW tags, enum option lists, metaConfig field titles/groups/options.
- Danish style: informal "du", imperative buttons ("Gem", "Annuller", "Slet", "Opret", "Rediger"), sentence case.
- Shared wording lives in `common.*` and is reused; do not create a second key for the same English string + meaning.
- Interpolation and plurals via i18next (`{{name}}`, `{{count}}`, `_one`/`_other`), never string concatenation of translated fragments.
- No page may be left half translated: a task converts every file in its folders.
- `src/spike/` is not touched.
- No changes to the `@mapcentia/gc2-agent-ui` or `@mapcentia/gc2-sdk` packages.
- Deviation from spec (builder's call, allowed by spec): no `i18next-browser-languagedetector`; a 10-line `detectLanguage` function is used instead because the rule is custom and must not cache.
- Work on branch `feat/i18n-danish`, not `main`. Use npm (`package-lock.json`).

## Review Focus

1. **`navigator.languages` empty or undefined** (embedded webviews, tests) → English, no crash. Test in Task 1.
2. **Look-alike and odd-cased tags**: `DA-dk` is Danish; `nb`, `dan`, `de` are not; `en-GB` counts as English and stops the search. Test in Task 1.
3. **Server messages containing `<`, `&` or `{{`** interpolated into a translated wrapper must appear verbatim, not HTML-escaped or re-interpolated. Test in Task 1.
4. **Counts of 0, 1 and many** in every plural message, in both languages ("1 table valgt", "0 tables valgt"). Structural test in Task 1 (every `_one` has an `_other` in both files).
5. **A key missing from `da.json`** must never show a raw key to a Danish user. Key-parity test in Task 1 plus `fallbackLng: 'en'`.

Also watch for, in review: texts defined at module level (column arrays, `fieldDefs`, stores) being evaluated before i18n is initialised — Task 1 pins the import order.

**Files:**
- Create: `src/i18n/testing/findHardcoded.ts`, `src/i18n/testing/pending.ts`
- Test: `src/i18n/testing/findHardcoded.test.ts`, `src/i18n/hardcoded.test.ts`

**Interfaces:**
- Produces:
  - `export interface Finding { file: string; line: number; text: string }`
  - `export function findHardcoded(source: string, fileName: string): Finding[]`
  - `src/i18n/testing/pending.ts`: `export const PENDING: string[]` — folders (relative to `src/`) not yet converted. Later tasks delete their entries.
  - Escape hatch: a `// i18n-ignore` comment on the same line or the line above suppresses a finding. Use it only for text the spec keeps English (menu-matching page titles, terms, raw enum values).

- [ ] **Step 1: Write failing unit tests for `findHardcoded`** — one `test` per rule, each with an inline source string:
  - flags JSX text: `<Button>Save</Button>` → 1 finding, text `Save`
  - ignores JSX text without two consecutive letters: `<span> — </span>`, `<b>{x}</b>`
  - flags string/template literals in JSX attributes `title, label, placeholder, okText, cancelText, description, tooltip, extra, message, help, content, alt, aria-label, emptyText, addonBefore, addonAfter`
  - flags the same names as object-literal properties with a string value: `{ title: 'Name', dataIndex: 'name' }` → flags `Name` only
  - flags the first argument of `message.success|error|warning|info|loading(...)` when it is a string or template literal
  - looks inside `cond ? 'A' : 'B'` and `a || 'B'` in all of the above positions
  - does not flag `t('…')` calls, `key`, `dataIndex`, `className`, `type`, `value` props
  - honours `// i18n-ignore` on the same and on the preceding line
  - flags template literals with substitutions: `` title={`Delete ${name}?`} ``

### Conversion procedure (applies to Tasks 3–9)

Each of these tasks converts its folders the same way. The task lists only what is specific to it.

- [ ] **A. Remove the task's folders from `PENDING`; run `npm test`** — expect the guard to FAIL listing every hard-coded string. That list is the worklist.
- [ ] **B. For each string:** add a key under the folder's group in `en.json` with the exact current English text, add the Danish translation under the same key in `da.json`, replace the literal with `t('group.key')` (or `i18n.t` outside components). Reuse `common.*` where the English string and meaning are identical.
- [ ] **C. Also convert what the guard cannot see:** strings in `.ts` files of the folder (stores, helpers), strings passed through variables, `Modal.confirm`/`modal.confirm` option objects, thrown `Error` messages that end up in the UI. Grep the folder for `'[A-Z][a-z]+ ` and `` ` `` to find them.
- [ ] **D. Replace** bare `n.toLocaleString()` on numbers with `formatNumber(n)`.
- [ ] **E. Mark agreed-English text** with `// i18n-ignore` (menu-matching page titles, raw server values) — never to silence a sentence.
- [ ] **F. Module-level texts** (column arrays, option lists declared outside a component) may call `i18n.t` directly; Task 1 guarantees init order.
- [ ] **G. Verify:** `npm test` PASS (guard + key parity + placeholders), `npm run typecheck` clean, `npm run build` succeeds.
- [ ] **H. Self-check the Danish** against Global Constraints: grep `da.json` for `skema|indeks|begrænsning|Constrain[^t]` → no hits; no English sentences left in the group's Danish values apart from listed terms.
- [ ] **I. Commit** — `feat(i18n): translate <folders>`
